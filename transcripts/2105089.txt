User: what is the need of the load function in the store.py?

LLM: In store.py, build() creates and saves the vector index; load() is the matching function that reads it back later.

Specifically, load(cfg) does three things:

1. Reads the FAISS index from:

data/interim/index/chunks.faiss

2. Reads saved chunk metadata from:

data/interim/index/chunks.jsonl

3. Reconstructs Chunk objects from that metadata and returns:

{
    "index": index,
    "metadata": metadata,
    "chunks": chunks,
}

So the need for load() is: after you have already built the knowledge base once, the retrieval system should not recompute OCR, chunking, embeddings, and indexing every time someone asks a question. It can simply load the saved FAISS index and chunk records, then search them.

Right now, pipeline.answer() creates retriever.Retriever(cfg), but Retriever is still unimplemented. When you implement retrieval, it will likely call store.load(cfg) inside Retriever.__init__() so it can search the saved index during retrieve().

In short: build() is for indexing time; load() is for question-answering time.

User: How exacly was roken overlap perfformed in chunk.py?

LLM: By "roken overlap" I think you mean token overlap.

In chunk.py, overlap is only applied inside _split_oversized(). That means overlap happens only when a single paragraph is too large:

if token_count > hard_max:
    _flush_pending(source, pending, out)
    out.extend(_split_oversized(source, paragraph, len(out), tokenizer, cfg))

Inside _split_oversized():

chunk_size = min(
    int(index_cfg.get("chunk_tokens", index_cfg.get("hard_max_tokens", 450))),
    _safe_window_tokens(tokenizer, cfg),
)
overlap = int(index_cfg.get("overlap", index_cfg.get("split_overlap_tokens", 40)))
overlap = max(0, min(overlap, chunk_size - 1))
stride = chunk_size - overlap

With your config.yaml:

index:
  chunk_tokens: 450
  overlap: 40

So the logic is:

chunk_size = 450 tokens
overlap = 40 tokens
stride = 450 - 40 = 410 tokens

Then it slices the oversized paragraph like this:

chunk 1: tokens 0   to 450
chunk 2: tokens 410 to 860
chunk 3: tokens 820 to 1270
...

So each next chunk starts 40 tokens before the previous chunk ended. That repeated 40-token region is the overlap.

Important detail: this overlap is not used when merging normal paragraphs. Small paragraphs are grouped up to target_max_tokens, and medium paragraphs become their own chunks. Only paragraphs bigger than hard_max_tokens are split with token windows and overlap.

Reflection:
I accepted a layout-aware paragraph chunking strategy because the existing layout detector already produces ordered text blocks that OCR converts into paragraph-separated text, giving the pipeline a meaningful structural unit without requiring an additional semantic segmentation model. I changed the original plan of fully semantic, layout-aware chunking because the corpus is structurally inconsistent and embedding-based boundary detection would introduce another source of segmentation error. I rejected pure fixed-size chunking as the primary method because it may arbitrarily separate related legal information such as party details, addresses, plot identifiers, and transaction context. For oversized paragraphs, I adopted a tokenizer-aware sliding-window split with configurable overlap, ensuring deterministic behavior and compliance with the embedding model’s context limit. I also reconsidered BGE-M3 in favor of multilingual-E5-small because the current design uses short paragraph-level dense retrieval, where E5 provides a simpler query-passage retrieval setup.
