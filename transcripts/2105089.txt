User: What does the load function in the store.py do?

LLM: In store.py, load(cfg) reloads the saved vector store from disk so retrieval can use it.

It does three things:

1. Loads the FAISS index

index = faiss.read_index(str(_index_path(cfg)))

This reads:

data/interim/index/chunks.faiss

unless cfg["index"]["path"] says otherwise.

2. Loads chunk metadata

with _metadata_path(cfg).open(...) as fh:
    metadata = [json.loads(line) for line in fh if line.strip()]

This reads:

data/interim/index/chunks.jsonl

That JSONL file stores chunk IDs, page IDs, doc IDs, text, token counts, etc.

3. Reconstructs Chunk objects

chunks = [
    Chunk(
        id=record["chunk_id"],
        doc_id=record.get("doc_id", ""),
        text=record["chunk_text"],
        page_ids=record.get("page_ids", [record["page_id"]]),
    )
    for record in metadata
]

So the return value is:

{
    "index": index,
    "metadata": metadata,
    "chunks": chunks,
}

In plain English: load() gives your retriever the FAISS index plus the matching chunk objects, so when FAISS says "vector row 7 is the best match," your retriever can map row 7 back to the actual Chunk text/page/citation metadata.

For your Retriever.retrieve(), you'll probably call store.load(cfg) during initialization, then use:

- loaded["index"] to search
- loaded["chunks"] to return matched Chunks
- loaded["metadata"] if you need extra citation/debug info

Functions To Call
In scripts/run_eval.py, the rough call order should be:

from doc_agent import config, pipeline
from doc_agent.retrieval.retriever import Retriever
from doc_agent.eval import metrics
from grading_kit.success_check import check

cfg = config.load()
retriever = Retriever(cfg)

tasks = load_jsonl("grading_kit/tasks.jsonl")

for task in tasks:
    question = task["question"]
    gold_pages = task["gold_pages"]

    retrieved = retriever.retrieve(question, k=cfg["retrieve"]["k"])
    retrieval_score = metrics.recall_at_k(retrieved, gold_pages, cfg["retrieve"]["k"])

    answer = pipeline.answer(question, cfg)
    answer_dict = answer.model_dump()

    exact_correct = check(task, answer_dict)
    grounded_score = metrics.groundedness(answer)
    citation_score = metrics.citation_accuracy(answer)

Then average the per-task scores.

Metric Meanings
ocr_f1(pred, gold)
This is mostly for OCR baseline evaluation, not normal A3 agent scoring. It compares OCR text against human transcription from labels.jsonl.

Example:

metrics.ocr_f1(predicted_ocr_text, gold_label["text"])

Your current mean ocr_f1 = 0.022 came from comparing bad OCR output against human gold text.

recall_at_k(retrieved, gold, k)
Use this for retrieval quality. retrieved should be the top-k Chunks from Retriever.retrieve(). gold should be task["gold_pages"].

Example task:

{
  "id": "date_dolil_99",
  "question": "What is the deed date on dolil_99?",
  "gold": "২৮/১০/২০০১",
  "gold_pages": ["dolil_99"],
  "verifiable": true,
  "judged": false,
  "needs_research": false
}

If retrieval returns chunks whose page_ids include dolil_99, then:

metrics.recall_at_k(retrieved_chunks, ["dolil_99"], 10)

should return 1.0. If not, 0.0.

groundedness(answer)
Use this to check whether the agent's final answer claims to be grounded and has citations. A simple version:

1.0 if answer.grounded is true and citations exist
0.0 otherwise

For abstention answers, you should handle correctness in success_check.check(), because only the task knows whether abstention was expected.

citation_accuracy(answer)
With the current signature, this can only check citation structure: does the answer contain valid citation objects with chunk_id and span? To check whether citations point to the gold page, use recall_at_k() on the cited chunks/page IDs against task["gold_pages"].

So in run_eval.py, you may compute:

citation_gold_match = metrics.recall_at_k(cited_chunks, task["gold_pages"], len(cited_chunks))

ece(confidences, correct)
Use this only if you report calibration. Inputs:

confidences = [answer.confidence for each task]
correct = [True/False from success_check.check()]

ECE measures whether confidence matches actual correctness. If your primary NFR is precision-first, this is optional unless your group chooses to report it.

subgroup_gap(scores_by_group)
Use this only if you report fairness/unbiasedness. Example groups might be scan type, page quality, or document type. If you do not have subgroup labels, do not invent this metric.

So doing PII redaction only before logging would protect logs, but it would not satisfy the A3 cross-cutting requirement.

What each seam is for:

after_ocr

Redacts/scrubs extracted OCR text before it is chunked, embedded, and indexed. This prevents PII from entering the knowledge base.

before_answer

Redacts/scrubs the final outgoing answer. This prevents the user-facing answer from leaking PII.

on_log

Redacts/scrubs logs/traces. This prevents PII from appearing in traces/run.jsonl or structured logs.

So the intended setup is:

OCR output
-> PII after_ocr
-> chunk/index

agent answer
-> PII before_answer
-> final answer

anything logged
-> PII on_log
-> log/trace file

You can additionally make sure PII redaction happens immediately before writing logs. That is good. But it should be an extra safety layer, not a replacement for after_ocr and before_answer.

hooks.register(hooks.ON_LOG, _scrub)

LLM: Sparse retrieval in real systems is basically search by words, identifiers, and exact surface forms, not by meaning.

Dense retrieval asks: which chunk is semantically close to this query embedding? Sparse retrieval asks: which chunk literally contains the important terms, numbers, names, dates, or near-matching spellings?

For legal/document RAG, engineers almost always want both.

A sparse retriever usually builds an inverted index: term -> list of chunks containing that term. The common scoring function is BM25. It rewards exact term overlap, rare terms more than common terms, repeated terms but with saturation, and reasonably short focused chunks.

In real production systems, engineers do not store metadata for decoration. Hybrid retrieval is usually: query -> normalize query -> dense search in FAISS -> sparse/BM25 search over normalized text and identifier fields -> merge candidate lists -> rerank or score-fuse -> return top-k chunks. RRF is popular because dense and BM25 scores are not naturally comparable.

User: Document frequency = how many chunks contain that term : How does BM25 store this

LLM: BM25 usually stores document frequency in a dictionary/map.

Example:

df = {
    "দলিল": 2,
    "গাজীপুর": 2,
    "20078": 1,
    "2500": 1,
    "রেজিস্ট্রার": 1
}

It builds that by iterating over chunks, taking set(chunk_tokens), and incrementing df[term] once per chunk. That is why দলিল appearing three times in one chunk still counts once for document frequency.

BM25 then converts document frequency into IDF, which means how rare and useful the term is. It may not keep raw df after building idf, because idf is what scoring actually uses.
