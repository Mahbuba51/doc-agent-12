| 0 Frame | Precision-first document-understanding agent for Land Registry Archives & Legal Aid: answer questions from scanned historical Dolils (Bangla-English handwritten deeds) with page citations. Headline target: Exact Match ≥95% on verifiable legal fields, F1 ≥0.92 overall. | Bangla Handwritten Dolil Dataset (Mendeley, CC BY 4.0, DOI 10.17632/yk3c3xy9vm.1): 653 scanned JPEGs, 651 content-usable (an earlier 609-page count wrongly excluded 44 files by a file-size heuristic — corrected after direct visual + integrity-check verification; `dolil_30` and `dolil_412` are the only two confirmed non-content pages, see `notebooks/eda.ipynb`). Of those 651, 105 are confirmed duplicate re-scans of another page (found via pHash/CLIP/ORB near-dup sweep, cross-checked against the printed stamp-paper serial where visible) and excluded from grouping/splitting, leaving **546 distinct document pages, ~65.5k words (est.)**, 2.33GB on disk (duplicates included, nothing deleted). Split 70/15/15 by deed via `data/deed_groups.csv` (capture-time EXIF grouping + manual review for the 36 pages with no EXIF), written to `data/splits.json`: train 382 / val 82 / test 82, 0 doc_id groups straddle a split. 38 pages (`dolil_313`–`324`, `431`–`462`) still lack EXIF and grouping review. | No model at this stage — framing only. Downstream: DocLayout-YOLO (layout), Qwen2.5-VL + GraDeT-HTR (reading), BGE-M3 (embed), Qwen3-4B-AWQ (agent controller). | Desk officers currently cross-reference paper Dolils manually — slow and error-prone with real legal consequences; the tool's source of truth is the scanned page itself, so grounded citation (not web search / general chat) is the right fit. | Agent must abstain rather than guess when evidence is weak; coverage is traded for trustworthiness given the precision-first NFR. | Justified against our own corpus (Section 1-4 of A1 form): domain, speciality, and NFR each point to specific pages/fields, not generic claims. | Offline batch ingest, online agent serving later (A4). Azure GPU VM (Standard_NC4as_T4_v3) planned for the served stack. | Track corpus version, split seed, and config snapshot via MLflow (Stage 8+); reproducible-by-corpus is the grading bar. |
| 1 Ingest+Enhance | Load and clean all 653 usable scanned Dolil pages so downstream layout/reading stages get a legible, unmodified-evidence image. | Same corpus; input is raw JPEGs in `data/raw/`, output is deskewed/denoised/binarized variants plus the untouched original+greyscale (kept as fallback since binarization can drop faint seals/matras). | Classical pipeline only: Pillow + OpenCV. No VAE/diffusion generative repair — rejected because a generative model could reconstruct, reshape, or remove a handwritten stroke and change a legally significant plot number, name, date, or amount. | Validate via a real integrity check (opens as a valid image, ≥200px both dimensions) — NOT a file-size threshold, which we tried first and it wrongly flagged 44 legible pages as corrupt; convert to greyscale; estimate skew via Hough/projection-profile search in [-4°,+4°] and rotate (fill=255); light 3x3 median denoise + non-local-means for show-through; Sauvola adaptive threshold (window 15, k=0.2, R=128) for a binary copy; scan-quality proxy = normalized high-pass blur variance (radius 3, /40.0), flag <0.35 as low-legibility; Unicode NFC text normalization + Bangla↔ASCII digit mapping downstream. | Deterministic, rule-based Stage 1 (no training loss) feeding Stage 2 layout detection; conservative parameters chosen to preserve thin strokes over aggressive cleanup. | Verified in `notebooks/eda.ipynb`: file counts, legibility-band histogram, pHash near-duplicate leakage check, before/after examples on representative pages (`dolil_13`, `dolil_20`, `dolil_11`). | Runs offline as a one-time batch job (`scripts/build_index.sh` upstream step) before the agent is served, avoiding repeated expensive image ops per query. | Preprocessing config (skew range, denoise, Sauvola params, quality threshold) is versioned alongside the corpus snapshot so a preprocessing change is traceable to its effect on downstream Exact Match. |

| 3 OCR | Turn each detected region into text a downstream chunker and a citing agent can trust. Precision-first: a plot number, date, or amount must be right to the character, so an unreadable region must come back unread rather than plausible. | 653 raw pages (651 content-usable, 546 distinct after duplicate resolution — see Row 0); 8 held-out scans in `grading_kit/heldout_pages/`, 7 with human-typed gold in `labels.jsonl` (`dolil_11` still TODO). Gold is typed by a Bangla reader, never model-generated — a model-written oracle would make the metric measure agreement-with-a-model. Illegible spots are `[?]`, not guesses. | **Baseline (measured, rejected): Qwen2.5-VL-3B-Instruct**, pretrained, single call per region, run locally. **Result: mean ocr_f1 0.022, median 0.000, 22/22 regions truncated at the 768-token cap** (`reports/ocr_baseline.json`) against a target of F1 ≥ 0.92. The model does not read Bangla handwriting: it confabulates fluent Bangla prose about a document-shaped image (`dolil_66` → "established on 20 May 1657… one of the oldest national memorials of an artist"), then loops until the cap. **Decision revised 2026-08-13: GraDeT-HTR promoted from deferred fallback to candidate reader**, pending a check that usable weights exist. 7B-AWQ escalation is NOT indicated — the gap is a missing capability, not missing parameters. | One VLM call per region, greedy (`do_sample=False`), regions concatenated in layout's reading order. Unicode NFC + Bangla→ASCII digit mapping shared with the metric. Scored by `eval/metrics.py:ocr_f1`: token-level F1, multiset counts so a repetition loop costs precision instead of scoring 1.0, `[?]`/`[illegible]` excluded from both sides so agreeing about failure cannot inflate the score. Ablation on `dolil_66` varied `max_pixels` (×4) and `repetition_penalty` (1.1) one at a time — all four cells still hit the cap, so no decoding knob rescues it. | One `Chunk` per PAGE, not per region, so Stage 4's legal-semantic chunker can still find deed and paragraph boundaries that span regions. A page whose regions all read empty yields no chunk rather than an empty one — an empty chunk would be indexed and retrievable as evidence for nothing. `doc_id` comes from the ingest sidecar or the deed grouping and is never invented, because it is what keeps the split document-level. Reader is injectable, so the assembly is testable without a GPU. | TDD throughout: 30 tests across `tests/test_ocr.py` and `tests/test_eval.py`, each watched fail first; the VLM is faked at the processor/model seam so CI stays CPU-only. `Reader.generation_stats` records per-region token count and cap-hit, because a short chunk looks identical whether the model stopped or we cut it off — and those call for opposite fixes. Baseline measured on a Kaggle T4 (fp16, `max_pixels` 1280·28²). Harness: `scripts/score_heldout.py`. | Offline batch, one pass before serving; nothing at query time re-reads a page. Local inference is a deliberate constraint (a production land-deed system handles sensitive records; hosted APIs may retain them) — noting precisely that THIS corpus is public CC BY 4.0 and carries no such risk itself. That constraint is what excludes the hosted OCR services that do read Bangla handwriting well, so D2 MEASURED is the point at which its cost became known rather than hypothetical. At the measured loop rate a full-corpus run is 11–33 GPU-hours, which exceeds a Kaggle session; a corpus run must be resumable and write incrementally. | `reports/ocr_baseline.json` snapshots model, dtype, `max_pixels`, full config block, per-page F1 and the predicted text — so the rejection is reproducible evidence, not an anecdote. Every reader change re-scores the same 7 gold pages and is judged on the delta against that file. The word count in `data/provenance.md` is explicitly NOT revised from this run: the reader under-extracts, which is the error that estimate already warns about. |
| 4 Index | Turn noisy page-level OCR text into retrievable, citation-preserving evidence chunks, then build a dense exact-search index for the agent. The stage must preserve page and paragraph boundaries because legal answers need traceable page citations and because layout paragraphs are stronger semantic units than arbitrary fixed windows. | Input is Stage 3 page-level `Chunk` objects, one per page, where layout/OCR has already concatenated detected regions in top-to-bottom order and separated text regions as paragraphs. Output is smaller `Chunk` objects plus sidecar metadata: `chunk_id`, `page_id`, `chunk_index`, `paragraph_indices`, `block_order_indices`, `chunk_text`, `token_count`, and `boundary_type`. `block_order_idx` is only OCR/layout reading order, not a detector block id. | `intfloat/multilingual-e5-small`, 384 dimensions, CPU, float32, normalized embeddings. Documents are embedded as `passage: ` + chunk text and query embeddings use `query: ` + query. Model/cache settings live in top-level `embed` config: `max_model_tokens` 512, `initial_batch_size` 8, `cache_dir` `.hf_cache`. | Hierarchical layout-aware paragraph chunking. Stage A recovers paragraphs from OCR paragraph separators and counts tokens with the E5 tokenizer. Stage B keeps normal paragraphs intact and merges adjacent very short paragraphs below 80 tokens up to a 200-300 token target, without crossing pages and with an admin/header boundary guard so registry labels are not blindly merged into deed-body text. Stage C applies overlapping token windows only to oversized paragraphs: `chunk_tokens` 450, `overlap` 40, stride = chunk size - overlap, final window may be shorter, and every split stores `split_part_idx` plus token offsets. | Vector storage is separated from metadata. `embed.encode(chunks, cfg)` returns only the normalized vector matrix; `store.build(chunks, vectors, cfg)` receives the original chunks alongside vectors so FAISS stores only vectors while `chunks.jsonl` stores the evidence metadata and text. This keeps the locked `Chunk` contract unchanged instead of adding fields to `contracts.py`. | Implemented inside the existing `src/doc_agent/index/` bodies only, following the fixed pipeline order: `chunk.split` -> `embed.encode` -> `store.build`. Verified with real E5 and FAISS smoke tests: 384-d float32 vectors, normalized, prefixed passage token length under 512, and FAISS `ntotal` matching chunk count. Static gates pass for the index package: Black, Ruff, mypy; full tests pass with 56 passed and 10 skipped. | Offline batch index build writes `data/interim/index/chunks.faiss` and `data/interim/index/chunks.jsonl`. FAISS uses `IndexFlatIP` over L2-normalized vectors, giving exact cosine-equivalent similarity without approximate-index tuning. CPU embedding is slower but reproducible and fits the current local/Kaggle development constraint. | Version and monitor the config values that change retrieval behavior: tokenizer/model name, chunk thresholds, overlap, normalization, FAISS type, and metadata schema. Rebuild the index whenever OCR, chunking thresholds, or embedding model changes. Sanity checks should assert vector dimension 384, metadata count equals FAISS `ntotal`, and all prefixed passages stay within the 512-token E5 limit. |
