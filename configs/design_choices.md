| 0 Frame | Precision-first document-understanding agent for Land Registry Archives & Legal Aid: answer questions from scanned historical Dolils (Bangla-English handwritten deeds) with page citations. Headline target: Exact Match ≥95% on verifiable legal fields, F1 ≥0.92 overall. | Bangla Handwritten Dolil Dataset (Mendeley, CC BY 4.0, DOI 10.17632/yk3c3xy9vm.1): 653 scanned JPEGs, 651 content-usable (an earlier 609-page count wrongly excluded 44 files by a file-size heuristic — corrected after direct visual + integrity-check verification; `dolil_30` and `dolil_412` are the only two confirmed non-content pages, see `notebooks/eda.ipynb`). Of those 651, 105 are confirmed duplicate re-scans of another page (found via pHash/CLIP/ORB near-dup sweep, cross-checked against the printed stamp-paper serial where visible) and excluded from grouping/splitting, leaving **546 distinct document pages, ~65.5k words (est.)**, 2.33GB on disk (duplicates included, nothing deleted). Split 70/15/15 by deed via `data/deed_groups.csv` (capture-time EXIF grouping + manual review for the 36 pages with no EXIF), written to `data/splits.json`: train 382 / val 82 / test 82, 0 doc_id groups straddle a split. 38 pages (`dolil_313`–`324`, `431`–`462`) still lack EXIF and grouping review. | No model at this stage — framing only. Downstream: DocLayout-YOLO (layout), Qwen2.5-VL + GraDeT-HTR (reading), BGE-M3 (embed), Qwen3-4B-AWQ (agent controller). | Desk officers currently cross-reference paper Dolils manually — slow and error-prone with real legal consequences; the tool's source of truth is the scanned page itself, so grounded citation (not web search / general chat) is the right fit. | Agent must abstain rather than guess when evidence is weak; coverage is traded for trustworthiness given the precision-first NFR. | Justified against our own corpus (Section 1-4 of A1 form): domain, speciality, and NFR each point to specific pages/fields, not generic claims. | Offline batch ingest, online agent serving later (A4). Azure GPU VM (Standard_NC4as_T4_v3) planned for the served stack. | Track corpus version, split seed, and config snapshot via MLflow (Stage 8+); reproducible-by-corpus is the grading bar. |
| 1 Ingest+Enhance | Load and clean all 653 usable scanned Dolil pages so downstream layout/reading stages get a legible, unmodified-evidence image. | Same corpus; input is raw JPEGs in `data/raw/`, output is deskewed/denoised/binarized variants plus the untouched original+greyscale (kept as fallback since binarization can drop faint seals/matras). | Classical pipeline only: Pillow + OpenCV. No VAE/diffusion generative repair — rejected because a generative model could reconstruct, reshape, or remove a handwritten stroke and change a legally significant plot number, name, date, or amount. | Validate via a real integrity check (opens as a valid image, ≥200px both dimensions) — NOT a file-size threshold, which we tried first and it wrongly flagged 44 legible pages as corrupt; convert to greyscale; estimate skew via Hough/projection-profile search in [-4°,+4°] and rotate (fill=255); light 3x3 median denoise + non-local-means for show-through; Sauvola adaptive threshold (window 15, k=0.2, R=128) for a binary copy; scan-quality proxy = normalized high-pass blur variance (radius 3, /40.0), flag <0.35 as low-legibility; Unicode NFC text normalization + Bangla↔ASCII digit mapping downstream. | Deterministic, rule-based Stage 1 (no training loss) feeding Stage 2 layout detection; conservative parameters chosen to preserve thin strokes over aggressive cleanup. | Verified in `notebooks/eda.ipynb`: file counts, legibility-band histogram, pHash near-duplicate leakage check, before/after examples on representative pages (`dolil_13`, `dolil_20`, `dolil_11`). | Runs offline as a one-time batch job (`scripts/build_index.sh` upstream step) before the agent is served, avoiding repeated expensive image ops per query. | Preprocessing config (skew range, denoise, Sauvola params, quality threshold) is versioned alongside the corpus snapshot so a preprocessing change is traceable to its effect on downstream Exact Match. |
| 2 Layout | Cut each scanned page into the regions the reader will crop, in reading order, without a trained detector or a GPU pass per page. Precision-first: a region boundary must never split a plot number, deed amount or date across two crops. | All 653 raw pages for the layout measurement below; correctness checked directly on the 8 held-out scans (4 flatbed-style, 4 phone photos), which is where the heuristic's real limits showed up. Input is whatever image the `Page` points at — raw scan or Stage 1's deskewed greyscale — since this stage does its own binarization. | Training-free **projection heuristic** (`layout.model: projection-heuristic`): no checkpoint, no GPU, no extra pinned dependency (OpenCV is already required). DocLayout-YOLO deferred, not rejected — it was only ever needed to feed a line-level HTR reader. **D1 rationale CORRECTED 2026-08-12**: this decision was originally defended with "the corpus has no tables and no multi-column pages", which is FALSE — `dolil_74` is a four-column তফসিল, and the gutter sweep below puts >=3.5% of pages in the multi-column band. The decision now stands on a narrower argument: D2 read whole pages in one VLM call, so layout governed only cropping. **That argument died with D2** (see `vision/ocr.py`), so this row is under active review — if the reader becomes line-level HTR, layout becomes load-bearing and BN-DRISHTI's public YOLOv5 line/word detector (CC-BY-SA-4.0, ships with GraDeT-HTR) is the candidate replacement. | Per-page Otsu binarization (crop to the paper first — an Otsu pass over a whole phone photo separates paper from the desk it was shot on, not ink from paper). A row counts as text when its ink >= `min_ink_frac` (0.01) of page width, which is what keeps dust and scan-edge artefacts from opening a band; blank runs <= `line_gap_px` (18) are treated as leading within a paragraph and merged, wider runs split blocks; per-band column extents give the horizontal bounds; `pad_px` 4; bands below `min_height_px` 10 or `min_width_px` 30 are dropped. **Measured** widest interior ink-free gutter / inked span over all 653 pages: p50 0.000, p90 0.026, p95 0.048, p99 0.109; >0.06 of span on 23 pages (3.5%), >0.15 on 4 (0.6%) — a LOWER bound on tabular pages, since a wide-gutter test finds two-column splits but misses dense tables with narrow inter-column gaps. | `Region` carries only `page_id`+`bbox`+`kind`, nothing richer, matching what Stage 3 actually reads. **Region = page, in practice.** Measured on the held-out scans: the 4 flatbed-style pages split into 3–9 regions, the 4 phone photos yield a single page-sized region and no amount of deskewing or adaptive thresholding produced blank rows on them — the writing genuinely runs continuously down the sheet. A page-sized region was the expected output under D2, not a segmentation failure, and finer cuts risked splitting a plot number across two crops. **Nothing downstream may assume more than one region per page.** Every region is emitted `kind="text"`; heading/table/figure are left unused rather than guessed at, since an unconsumed class nobody evaluates is untested surface. The print/handwriting boundary found in D2 MEASURED (2) is the first real candidate use for `kind`. | 12 tests in `tests/test_layout.py`, TDD, CPU-only, deterministic, synthetic images only so CI needs no corpus: band splitting/merging, reading order, bbox tightness and page-bound clamping, blank pages, speckle below the size floor, dark uneven scan grounds, and EXIF-rotated pages (cv2.imread applies the orientation tag, so bboxes are in DISPLAY coordinates — the reader's crop must match, which `vision/ocr.py` handles with `exif_transpose`). **Known unhandled:** some pages are rotated 90° *in content* (e.g. `dolil_429`), which EXIF correction does not fix and which defeats horizontal projection outright; prevalence not yet measured. | Offline batch, one pass before serving; nothing at query time re-segments a page. Cost is negligible — no model to load, no GPU, milliseconds per page on CPU — which is why it was never the bottleneck in the 11–33 GPU-hour corpus-run estimate. If layout becomes line-level, that changes: a YOLOv5 detector adds a GPU pass per page and an AGPL-3.0 dependency (ultralytics), which is a licensing question for the A4 deployment, not just a compute one. | All five thresholds live in `configs/config.yaml:layout` and are versioned with the corpus snapshot, so a parameter change is traceable to its effect on downstream `ocr_f1`. Region counts per page are logged (`logging_conf`) so a segmentation regression shows up as a distribution shift rather than a silent quality drop. The gutter measurement is reproducible from `notebooks/eda.ipynb`. The gutter measurement (3.5% / 0.6% of pages) is recorded as the TRIGGER CONDITION for revisiting this decision: if `ocr_f1` comes out materially worse on tabular pages once a working reader is scored at scale, that is the signal to build real column-aware segmentation rather than lean on the cropping argument. |
| 3 OCR | Turn each detected region into text a downstream chunker and a citing agent can trust. Precision-first: a plot number, date, or amount must be right to the character, so an unreadable region must come back unread rather than plausible. | 653 raw pages (651 content-usable, 546 distinct after duplicate resolution — see Row 0); 8 held-out scans in `grading_kit/heldout_pages/`, 7 with human-typed gold in `labels.jsonl` (`dolil_11` still TODO). Gold is typed by a Bangla reader, never model-generated — a model-written oracle would make the metric measure agreement-with-a-model. Illegible spots are `[?]`, not guesses. | **Baseline (measured, rejected): Qwen2.5-VL-3B-Instruct**, pretrained, single call per region, run locally. **mean ocr_f1 0.022, median 0.000, 22/22 regions truncated at the 768-token cap** (`reports/ocr_baseline.json`) against a target of F1 >= 0.92. It does not read Bangla handwriting: it confabulates fluent Bangla prose about a document-shaped image (`dolil_66` -> "established on 20 May 1657... one of the oldest national memorials of an artist"), then loops until the cap. **Escalated across generations, not just sizes: Qwen3.5-9B** (Apache-2.0, natively multimodal, 201 languages; fp16 on 2xT4, ~1.6M px, `enable_thinking=False`) fails identically -- `dolil_208` f1 0.028, inventing deed boilerplate instead of universities. A better prior, not better reading. **But it reads PRINT correctly**: on `dolil_20` (f1 0.093, our highest) "ONE RUPEE EIGHT ANNAS", "Sub-Registrar Raipur, Dist. Noakhali" and the Act/registration stamp block all came out right (5 of 7 probe strings), while the handwriting on the same page came back Bangla-shaped, deed-structured and wrong. **So the finding is not "Qwen fails" but "the VLM reads print on these scans and cannot read the handwriting"** -- and 7B-AWQ is not worth trying, because the gap is a missing capability, not missing parameters. **Decision 2026-08-13/14: GraDeT-HTR promoted** from deferred fallback to candidate reader (EMNLP 2025; code MIT, recognition weights request-only, BN-DRISHTI line detector public CC-BY-SA-4.0), pending confirmation that weights are obtainable. | One VLM call per region, greedy (`do_sample=False`), regions concatenated in layout's reading order; Unicode NFC + Bangla->ASCII digits shared with the metric. Scored by `eval/metrics.py:ocr_f1`: token-level F1, multiset counts so a repetition loop costs precision instead of scoring 1.0, `[?]`/`[illegible]` excluded from both sides so agreeing about failure cannot inflate the score. Ablation on `dolil_66` varied `max_pixels` (x4) and `repetition_penalty` (1.1) one at a time -- all four cells still hit the cap, so no decoding knob rescues it. **Headline metric is `macro_f1_by_deed`, not `mean_f1`**: 10 of the 17 gold pages are one deed (`deed_p0038`), so a per-page mean largely measures one scribe. Both are reported; the gap between them measures how lopsided the sample is. Read the predicted TEXT, not the F1 -- the best-scoring ablation cell was the one that read least (14 words, one a 90-digit run). | One `Chunk` per PAGE, not per region, so Stage 4's chunker can still find deed/paragraph boundaries that span regions. A page whose regions all read empty yields no chunk rather than an empty one -- an empty chunk would be indexed and retrievable as evidence for nothing. `doc_id` comes from the ingest sidecar or the deed grouping and is never invented; pages absent from the grouping (105 duplicate re-scans + 2 non-content) are EXCLUDED with a warning rather than crashing the reader. Reader is injectable, so the assembly is testable without a GPU. **Open direction:** the print/handwriting boundary suggests a hybrid reader (VLM for printed regions, HTR for handwritten), which would give `Region.kind` a real job -- today every region is `kind="text"`. | TDD throughout: 30 tests across `tests/test_ocr.py` and `tests/test_eval.py`, each watched fail first; the VLM is faked at the processor/model seam so CI stays CPU-only. `Reader.generation_stats` records per-region token count and cap-hit, because a short chunk looks identical whether the model stopped or we cut it off — and those call for opposite fixes. Baseline measured on a Kaggle T4 (fp16, `max_pixels` 1280·28²). Harness: `scripts/score_heldout.py`. | Offline batch, one pass before serving; nothing at query time re-reads a page. Local inference is a deliberate constraint (a production land-deed system handles sensitive records; hosted APIs may retain them) — noting precisely that THIS corpus is public CC BY 4.0 and carries no such risk itself. That constraint is what excludes the hosted OCR services that do read Bangla handwriting well, so D2 MEASURED is the point at which its cost became known rather than hypothetical. At the measured loop rate a full-corpus run is 11–33 GPU-hours, which exceeds a Kaggle session; a corpus run must be resumable and write incrementally. | `reports/ocr_baseline.json` snapshots model, dtype, `max_pixels`, full config block, per-page F1 and the predicted text — so the rejection is reproducible evidence, not an anecdote. Every reader change re-scores the same 7 gold pages and is judged on the delta against that file. The word count in `data/provenance.md` is explicitly NOT revised from this run: the reader under-extracts, which is the error that estimate already warns about. |
| 4 Index | Turn each page's transcribed text into retrievable passages: real chunk boundaries a citing agent can point to, sized to fit the embedding model's context window without silent truncation, and vectors a similarity search can actually match against a Bangla-English legal query. | Full corpus is 546 distinct pages (~65,500 words, est.). Stage 3's only measured reader (Qwen2.5-VL-3B) is not viable at that scale: mean `ocr_f1` 0.022 on held-out gold pages, confabulating fluent unrelated prose rather than reading the handwriting (`reports/ocr_baseline.json` — see Row 3). Indexing that output at full-corpus scale would fill the store with invented text, which is worse than an empty store. **Plan instead of a full-corpus run right now:** index the pages that already have a real, human-typed gold transcription in `grading_kit/labels.jsonl` (`status: "done"`, 17 pages / 2,398 words, ~3.1% of the corpus by page count) — proving `chunk -> embed -> index -> retrieve` works end-to-end on real, human-verified Bangla legal text, honestly reported as a small subset rather than full-corpus coverage. Chunking/embedding/indexing operate on whatever text a `Chunk` carries regardless of source, so the same code indexes the real corpus unchanged once Stage 3 has a working reader. | No trained model for chunk boundaries — rule-based paragraph/token-window splitting. Embedding: **`intfloat/multilingual-e5-small`**, pretrained (not fine-tuned), 384-dim, CPU, via `sentence-transformers` — off the shelf and unmodified, the pipeline's reproduced-published-method box for A2 form Section 3. Vector index: **FAISS `IndexFlatIP`** (exact search, not ANN) — at demo-to-mid-hundreds-of-pages scale, approximate search buys nothing and costs recall. | Paragraphs split on blank lines; an `_admin_like` check (short line + digits + separators, or an explicit marker like "date"/"serial"/"registry") stops a structured line (a date, a serial number) from merging into an adjacent prose paragraph even when both are short. Below `merge_below_tokens` (80) and under `target_max_tokens` (300)/`preferred_max_tokens` (350), short same-kind paragraphs merge; at/above that they stand alone; above `hard_max_tokens` (450) a paragraph is token-windowed with `overlap` (40 tokens) using the real tokenizer's character offsets, so no chunk can silently exceed what the embedder will actually consume. `_safe_window_tokens` additionally caps the window by the embed model's `max_model_tokens` (512) minus the "passage: "/"query: " prefix's own token cost, so the hard cap and the embedder's real limit are kept consistent on purpose. Embedding follows e5's asymmetric-prefix convention (`document_prefix: "passage: "` at index time, `query_prefix: "query: "` at retrieval); `normalize_embeddings: true` so FAISS inner product is exactly cosine similarity. | Chunk-level metadata (`paragraph_indices`, `block_order_indices`, `token_count`, `boundary_type`, `chunk_id`) is tracked in `chunk.py` and threaded through `store.build()` into `chunks.jsonl`, so a retrieved `chunk_id` traces back to exactly which paragraph(s) or token-window of which page it came from — the citation trail Stage 6 will need. `store.load()` rebuilds `Chunk` objects straight from that sidecar, so retrieval never needs the original OCR/chunking run in memory. | `chunk.py`/`embed.py`/`store.py` are implemented and pass `ruff`/`black`/`mypy` clean. **Open gap, not yet closed:** unlike Stages 1–3, which each have their own `tests/test_*.py`, Stage 4 has no dedicated test file yet — the handbook's "per-stage unit tests" CI gate is not satisfied for this stage. The demo index described in Data above IS built and executed in `notebooks/kb_demo.ipynb`: 17 pages -> 119 chunks, 384-dim, `faiss:flat`; the retrieval example (query "দলিলে টেনু সাব্বির পিতার নাম কী?") correctly returns `dolil_605#c0068` at score 0.880, assertion passing. The missing test file is the one gap still open. | Offline batch: the index is rebuilt whenever the corpus or these chunk/embed params change; nothing is computed at query time except `encode_query()` plus one FAISS search. Runs on CPU (`device: cpu`), matching the rest of the offline-batch ingest profile — only Stage 3's reader needs a GPU. | `index`/`embed` params (chunk sizes, overlap, model name, dimension) are versioned in `config.yaml` alongside the corpus snapshot. Re-embedding is all-or-nothing: no incremental migration path exists if `embed.model` changes, so a model swap means a full rebuild, not a partial one. The metric to track going forward is corpus coverage (currently 3.1% pages / 3.7% words, built and demonstrated) climbing toward 100% as Stage 3's reader question gets resolved — that number, not chunk count, is the real signal of whether this is a demo or the production KB. |
| 5 Retrieval | Retrieve a small, high-precision evidence set for Bangla-English legal questions while preserving the existing `Retriever.retrieve(query, k)` -> `list[Chunk]` contract and the agent's weak-evidence logic. The retriever must handle both semantic paraphrases and exact legal identifiers such as dates, section numbers, amounts, document ids, and named entities. | Use the Stage 4 index artifacts: FAISS dense index plus `chunks.jsonl` sidecar metadata. The current reliable KB is built from the human-gold subset rather than the outdated interim files; chunk metadata includes `bm25_tokens`, digit/date/amount/identifier candidates, page/document ids, and text needed to reconstruct `Chunk` objects. | Dense retrieval uses the already indexed `intfloat/multilingual-e5-small` embeddings with `query:`/`passage:` prefixes and 384-dimensional normalized vectors. Lexical retrieval uses `rank_bm25.BM25Okapi`. Reranking uses `BAAI/bge-reranker-v2-m3` through SentenceTransformers `CrossEncoder`. | At query time, load the FAISS store with `store.load(cfg)`, embed the query with `encode_query`, run dense FAISS search, run BM25 over `metadata[*]["bm25_tokens"]`, combine dense and lexical rankings with weighted reciprocal rank fusion, optionally rerank the candidate pool, then return the final top `k` chunks with updated scores. BM25 is cached as `bm25.pkl` plus `bm25.meta.json`, invalidated by `chunks.jsonl` SHA256, record count, token field, sparse schema version, and BM25 parameters. | Keep existing public function signatures and data contracts unchanged. Do not introduce PostgreSQL for this stage; use the JSONL sidecar as the lexical corpus. RRF combines ranks rather than raw dense/BM25 scores, with dense weight `0.65`, BM25 weight `0.35`, and `rrf_k=60`. Candidate pool size is `k * 4`, rerank top-n is `30`, final default `k` is `10`, and adaptive retrieval still uses `k_step=10`, `k_max=40`, `weak_threshold=0.35`. | Implement only in allowed files: `src/doc_agent/retrieval/retriever.py`, `src/doc_agent/retrieval/rerank.py`, `configs/config.yaml`, `pyproject.toml`, and `uv.lock`. Add `rank-bm25>=0.2.2,<0.3`. No tests are added for now by instruction. Validation completed with `ruff`, `black --check`, import/compile checks, and config parsing; end-to-end retrieval is deferred until a fresh current index is available. | Runtime needs the FAISS index, `chunks.jsonl`, the BM25 cache beside the index, the embedding model, and the reranker model. Dense retrieval and BM25 can run locally on CPU; reranking is heavier and should be treated as the main latency/memory cost. No external search service or database is required for deployment in this stage. | Track retrieval config versions, sparse schema version, `chunks.jsonl` hash, BM25 cache rebuilds, dependency lock state, model names, top score, weak-evidence rate, recall@k on the gold set, reranker impact, and failure cases involving exact identifiers. Rebuild the BM25 cache whenever chunks or sparse-token parameters change. |
